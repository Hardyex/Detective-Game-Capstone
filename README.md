# 🔎 Detective Game Capstone

> **2D Detective Adventure Game**  
> A 2D detective adventure game developed as a Software Engineering Capstone Project.

---

## 📌 About The Project

**Detective Game Capstone** is a 2D detective adventure game focused on **investigation, exploration, evidence collection, and puzzle solving**.

The player takes the role of a detective who investigates mysterious cases by:

- 🕵️ Exploring environments
- 🔍 Examining objects and locations
- 🧩 Collecting and analyzing evidence
- 💬 Interacting with characters
- 🧠 Connecting clues to solve puzzles
- 📖 Progressing through the story

The project is developed using **Unity** and managed collaboratively through **Git & GitHub**.

---

## 🎮 Game Concept

The game combines classic detective elements with 2D adventure gameplay.

### Core Gameplay Loop

```text
Explore
   ↓
Investigate
   ↓
Collect Evidence
   ↓
Talk to Characters
   ↓
Connect Clues
   ↓
Solve Puzzle
   ↓
Progress Story
```

# 🚀 Getting Started

## 1. Clone the Repository

If you don't have the project on your computer yet, open **Git Bash** or **Terminal** and run:

```bash
git clone https://github.com/Hardyex/Detective-Game-Capstone.git
```

Move into the project directory:

```bash
cd Detective-Game-Capstone
```

Switch to the development branch:

```bash
git checkout dev
```

> This step only needs to be done when setting up the project for the first time.

---

## 2. Open the Project in Unity

Open **Unity Hub**.

Select:

```text
Add
→ Add project from disk
```

Then select:

```text
Detective-Game-Capstone/
└── 2D_Detective_Game/
```

Open the project using the **Unity version specified by the team**.

### ⚠️ Important

Do **not** worry if folders such as these appear after opening Unity:

```text
Library/
Temp/
Logs/
UserSettings/
```

These folders are automatically generated by Unity and are excluded from Git through `.gitignore`.

# 🌿 Git Workflow

## 3. Before Starting New Work

**Always update your local `dev` branch before starting a new task.**

First:

```bash
git checkout dev
```

Then:

```bash
git pull origin dev
```

After that, create your own feature branch:

```bash
git checkout -b feature/<feature-name>
```

### Examples

```bash
git checkout -b feature/dialogue-system
```

```bash
git checkout -b feature/inventory-system
```

```bash
git checkout -b feature/evidence-system
```

```bash
git checkout -b feature/main-menu
```

### Branch Naming Convention

| Prefix | Usage |
|---|---|
| `feature/` | New functionality |
| `fix/` | Bug fixes |
| `ui/` | UI-related work |

Examples:

```text
feature/dialogue-system
feature/evidence-system
fix/player-movement
ui/inventory-menu
```

---

# 💻 Development Rules

## 4. Write Code in Your Feature Branch

All development should be done on your own feature branch.

Example:

```text
feature/dialogue-system
```

Avoid making changes directly on:

```text
main
dev
```

### Recommended Project Area

Most gameplay code should be placed under:

```text
2D_Detective_Game/Assets/_Project/
```

Keep your changes organized according to the existing project structure.

---

## 🧪 Test Before Committing

After completing your task:

1. Open the project in Unity.
2. Enter **Play Mode**.
3. Test the feature you implemented.
4. Check the Unity Console.
5. Make sure there are no unexpected red errors.
6. Verify that your changes do not break existing gameplay.

> **Do not push code that has not been tested.**

---

# 📤 Commit & Push

## 5. Check Your Changes

Before committing:

```bash
git status
```

Review which files were modified.

---

## 6. Add Changes Selectively

### ✅ Recommended

Add only the project source files you actually changed:

```bash
git add 2D_Detective_Game/Assets/_Project/
```

If you intentionally changed important Unity project settings, add them separately:

```bash
git add 2D_Detective_Game/ProjectSettings/
```

### ❌ Do NOT use

```bash
git add .
```

This project uses Unity, which generates many local files and folders.

Using:

```bash
git add .
```

can accidentally stage files that should not be committed.

---

# 📝 Commit Convention

Use clear and descriptive commit messages.

### New Feature

```bash
git commit -m "feat(dialogue): implement dialogue typing UI system"
```

### Bug Fix

```bash
git commit -m "fix(player): fix player movement collision"
```

### UI Changes

```bash
git commit -m "ui(inventory): improve inventory layout"
```

### Commit Format

```text
type(scope): description
```

### Common Types

| Type | Meaning |
|---|---|
| `feat` | New feature |
| `fix` | Bug fix |
| `ui` | UI changes |
| `refactor` | Code restructuring |
| `docs` | Documentation |
| `chore` | Project/configuration changes |

Keep commit messages:

- Short
- Specific
- Easy to understand

---

## 7. Push Your Feature Branch

After committing:

```bash
git push origin feature/dialogue-system
```

Replace `feature/dialogue-system` with your actual branch name.

Example:

```bash
git push origin feature/evidence-system
```

---

# 🔀 Pull Request

## 8. Create a Pull Request

After pushing your branch to GitHub:

1. Open the project repository on GitHub.
2. Find your recently pushed branch.
3. Click **Compare & pull request**.
4. Set the target branch to:

```text
dev
```

5. Add a short and clear Pull Request title.
6. Describe what you implemented.
7. Mention any important changes or known issues.
8. Create the Pull Request.
9. Notify the team leader for review.

### PR Direction

```text
feature/your-branch
        │
        ▼
       dev
```

Do **not** create a PR directly into `main` unless the team explicitly agrees.

---

# 👀 Pull Request Checklist

Before requesting a review, make sure:

- [ ] Code has been tested in Unity
- [ ] No unexpected Console errors
- [ ] Changes are limited to the intended feature
- [ ] No `Library/` or `Temp/` files are included
- [ ] Commit message follows the convention
- [ ] PR targets `dev`
- [ ] PR description explains the changes
- [ ] Existing features still work
